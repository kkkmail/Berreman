# Architecture critique -- .spec-md cycle 1

## Summary

Whole-spec review of the 0033 bundle (`.spec-md` + the 26-step `.spec-jsonl`). The current `git diff HEAD` contains only the claim-check wording fix to §A.0 ("only catalogue proxy") plus `.history`/`cost.json` ledger entries — exactly what the recorded history says landed — so findings concern the architecture the plan would produce, not code already written. A prior draft of this critique existed at this path from before the spec-cycle commit; this run re-verified its findings against the repo and supersedes it. The spec is architecturally strong — placements are forced by the real dependency graph and the spec usually says so. The most important finding is a layering/scheduling hole: Part F promises the `Ui/Validation.fs` helpers "move with the editors … never duplicated," but no step owns that move, leaving steps 21/23 citing helpers they cannot reach.

## Layering

Verified against the actual `.fsproj` references: `Controls` has zero project references (domain-free by construction); `Domain` references core `Berreman` and `Analytics` (hence `OpticalProperties` transitively); `TestWindows` references only `Domain` and `Controls`; `Ui` references Domain/Storage/Optimization/Controls/Analytics.

- **Steps 21 and 23 cite unreachable helpers.** Step 21 (Domain) anchors `SetRepeatCount`'s rejection rule to `OpticalConstructor.Ui/Validation.fs:56` and step 23 (TestWindows) surfaces `imaginaryIndexGainWarning` (`Validation.fs:92`) — but Domain cannot reference Ui (the edge would be circular) and TestWindows does not reference Ui. Part F's steering text mandates the move, yet no step's `how_to` performs it and step 23's `touches` omits `OpticalConstructor.Ui` (which a move must re-point) — contrast step 19, which explicitly owns the `MaterialPreview` spectral-axis helper move. As written the worker must either duplicate the rules (Part F forbids it) or improvise an unauthorized cross-project move. The reuse critic reached the same conclusion (its F2); I confirm it independently from the project graph. Smallest fix: assign the move (Ui → Domain, re-point Ui) to step 21, with Ui in `touches`.
- **Everything else routes correctly, and several placements are forced.** Core `Berreman.fsproj` cannot reference `OpticalProperties`, so `RhoWithDispValue.toRhoWithDisp` as a type extension in `Active.fs` (step 9) is necessity, not style. Step 17's chart move into Controls is feasible: `ExperimentChart.fs:3-5` documents the model as "Domain-neutral (no Berreman types)," and the pure `ChartStyle` module that `ChartWindow.fs` depends on lives *inside* `ExperimentChart.fs:147`, so the two-file move carries it. Step 19's `nkDispersionChart` in TestWindows is the only workable home — it needs both Analytics and the Controls chart type, and no lower project sees both.
- Two transitive-reference notes. Step 19's premise that Analytics is unreachable from TestWindows "today" is slightly off — nothing in the repo sets `DisableTransitiveProjectReferences`, so Analytics already flows through Domain; the explicit reference is still correct hygiene for a direct dependency. Conversely, step 13's `MaterialComplexity.toProperties` makes Domain consume the `Active.fs` extension with `OpticalProperties` visible only transitively through Analytics (a charting project); a direct `OpticalProperties` ProjectReference on Domain when step 13 lands would keep a future cleanup of the odd Domain→Analytics edge from breaking material assembly at a distance.

## Separation of concerns

The proxy split is well shaped: `MaterialProxy.createInMemory` taking an injected `samplesReferencing : MaterialId -> Sample list` (step 6) keeps referential-integrity policy inside the material seam without a bidirectional proxy dependency, and step 26 wires it to the SampleProxy store one-directionally. Building `SampleStackEditor` as a new pure Domain edit model rather than growing `StackEditor.StackMsg` (step 21) is correctly reasoned — `applyStackMsg` transforms a resolved engine `OpticalSystem` (`StackEditor.fs:161,176`) that has no material ids to select by — and both editors' pure edit models honour the testable-without-a-window rule. One watch item: steps 14/24 grow `TableAndElementRotationView.fs` (~1600 lines) by two more bays of flatten/verb wiring; that follows the existing host precedent, but the file is becoming the de-facto composition monolith the WinForms-portability caveat will eventually resist.

## Consistency

The spec goes with the grain: the new controls copy the `LibraryControls` `Row`/`State`/`Handlers`/`UiIds` shape, relabeling `MaterialError.UnknownMaterialId` to carry `reason : string` (step 2) brings the one bare-payload error case up to the CLAUDE.md rule, and the Part A reversal of spec-010's "only expanded films exist" decision is honestly recorded against what `RepeatBuilder.fs:1-8` actually says. One divergence: steps 15/16 prescribe `[<Literal>]` UiIds, but all eight existing Controls `UiIds` modules use plain `let` bindings — including function-valued row ids that *cannot* be `[<Literal>]`, and both new bays list entries so they will need one. The reuse critic (F7) and the claim-checker (claim 22) flagged the same; the sibling convention should win.

## Spec fit

Coverage of the operator's preliminary spec (0027-035 rev. 4) is complete — §§2-9 each map to concrete steps, §10's "not in this task" list is respected (no disk persistence, no schema work), all six contract-table placeholders have matching ADD/IMPLEMENT steps, and Part G's typed unsupported-formula error for RII 8/9 is an honest negative scope. Two internal-coherence defects remain:

1. **Constraint 0.1 contradicts Part B as written.** 0.1 ends "No solver file changes in this spec," yet steps 7–10 add types to `Berreman/Berreman/Dispersion.fs` and new `Rho` builders to `Active.fs`. The intent (strictly additive `…Value` data; existing engine unions untouched, as step 7 itself says) is clear, but a literal-minded worker or judge can read steps 7–10 as violating a binding constraint. Reword 0.1.
2. **Constraint 0.3 contradicts step 2.** 0.3 says "The only `OpticalConstructor.Storage` change is Part G's import-parser breadth," but step 2 touches Storage (the `MaterialImport` entry builders at `MaterialImport.fs:80,109,144` are re-typed to `MaterialId`). Mechanical fallout of the id elevation, but "only" is falsified; qualify it.

## Evolvability

The in-memory stores are the right seam — a disk-backed implementation replaces `createInMemory` behind the same `[<ReferenceEquality>]` record at one composition site (`Program.fs:125-127`). Step 1 keeping `materialId` a string until step 2 elevates it re-writes the seeds twice in consecutive steps — accepted churn that keeps each step landable. One soft spot: `MaterialEntry` will carry both `complexity : MaterialComplexity option` (source of truth when `Some`) and `properties`, with coherence maintained only by save-time discipline (steps 13/23); nothing in the types prevents a diverged entry. One recorded sentence (e.g., `properties` is a derived cache; `complexity` wins) turns that invariant into a contract before a future serialization slice has to guess.

## Risks

- **Step 1 concentrates the arc's risk**: new structure type, delete the string branching and glass fallback, re-seed all 11 samples, rebuild `sampleToSystem`, re-point the sweep builders — the largest step and everything in Part A depends on it. Its equal-to-hand-built-system acceptance is a strong pin, but it is the step most likely to need a re-spawn.
- **Step 14's acceptance is a transient invariant step 24 deliberately violates.** Step 14 requires "no bay labelled Library"; step 24 re-mints `BayNames.library` for the samples workbench. The deleted identifier protects code references in between, but string-literal `"Library"` assertions in `Ui.Tests` are not compile-protected; a parenthetical in step 24 acknowledging the supersession would keep a worker from "fixing" the step-14 test the wrong way.
- **Step 12's Brendel–Bormann model needs the Voigt profile** (complex error function); the step names reference values but no numerical kernel. The vendored MathNet.Numerics ships special functions — one clause steering the worker there prevents a hand-rolled Faddeeva.

## Bottom line

I would ship this spec into implementation after a light spec-text revision pass — no re-spawn of the cycle warranted. The citations are trustworthy, the layering decisions are verified against the real project graph rather than asserted, and the recorded decisions reflect what the code says. The items to patch are spec-text-sized: schedule the `Validation.fs` helper move with an owning step (the one genuine layering hole — it otherwise forces a worker into an unrecorded architectural choice), reword constraints 0.1 and 0.3 so the binding text stops contradicting the steps it binds, and align the UiIds prescription with the eight siblings. None of these blocks Parts A–D from starting. The judge decides.
